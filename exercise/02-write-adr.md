# งานที่ 2: เขียน ADR สำหรับความต้องการใหม่ (ประมาณ 20 นาที)

> **เชื่อมโยงกับการบรรยาย:** T3 (GPT-4 แบบ zero-shot ให้ผลที่สอดคล้องกัน แต่ *ครบถ้วนน้อยกว่ามนุษย์* ส่วน few-shot ช่วยลดช่องว่างได้มาก), AICH3 (บริบท), สัปดาห์ที่ 10 (message broker)
> **คำถาม:** ADR ที่ AI เขียนดีขึ้นแค่ไหน เมื่อให้ตัวอย่างและบริบทจริงแก่ AI

อ่าน [สถานการณ์ (ภาษาไทย)](../docs/scenario.th.md) ก่อน: ความต้องการ **R-12** ว่าด้วยสิ่งที่เกิดขึ้นหลังจากลูกค้าสั่งซื้อสินค้า

ในแต่ละ run ให้เริ่ม **แชตหรือ session ใหม่** แล้วส่งข้อความด้านล่าง โดยแทนที่ `<paste R-12 here>` ด้วยข้อความ R-12 ภาษาอังกฤษที่อยู่ในกรอบอ้างอิงของ scenario

**Run a: ไม่มีตัวอย่าง (zero-shot)** → [`outputs/2a-adr.md`](outputs/2a-adr.md)
```
Follow prompts/2-write-adr.md
run: a
context: none
requirement: <paste R-12 here>
language: Thai
```

**Run b: มีตัวอย่าง + บริบท** → [`outputs/2b-adr.md`](outputs/2b-adr.md)
```
Follow prompts/2-write-adr.md
run: b
context: docs/scenario.md, docs/adr/0001-use-redis-for-cart-storage.md, system/online-boutique/src/checkoutservice/main.go
requirement: <paste R-12 here>
language: Thai
```

> บรรทัด `language: Thai` ทำให้ agent เขียน ADR เป็นภาษาไทย (หัวข้อของ template และชื่อทางเทคนิคยังคงเป็นภาษาอังกฤษ) หากต้องการภาษาอังกฤษให้ลบบรรทัดนี้ **ใช้ภาษาเดียวกันทั้ง Run a และ Run b** เพื่อให้เปรียบเทียบกันได้

> ใน Run a ให้ตรวจว่า agent ไม่ได้อ่านไฟล์อื่นนอกจาก template จริง ๆ หาก agent เปิด `docs/scenario.md` ให้บันทึกไว้ใน prompt log เพราะจะทำให้การเปรียบเทียบเปลี่ยนไป

## เปรียบเทียบ a กับ b

| เกณฑ์ | Run a | Run b |
|---|---|---|
| ใช้ตัวเลขจาก scenario หรือไม่ (latency, ช่วงพีก, ข้อจำกัดของ MailFast) | ไม่ใช้ ไม่มีตัวเลขเลย และระบุใน Decision drivers ว่า "ไม่กำหนดตัวเลขที่ยังไม่ได้รับมา" | ใช้ครบ: p95 ≤ 500 ms (ปัจจุบันประมาณ 300 ms), 200 orders/s, MailFast p95 1.5 s / p99 8 s / ล้มเหลว 0.5% / 50 อีเมล/วินาที, แต้มภายใน 1 นาที |
| ทางเลือกที่พิจารณา (ระบุ) | เรียกตรง, message broker (ไม่ระบุเทคโนโลยี), orchestrator กลาง | Synchronous gRPC, RabbitMQ, Kafka พร้อมข้อดีข้อเสียที่อ้างตัวเลขและทักษะทีม |
| จัดการแต้มสะสมแบบ "ครั้งเดียวเท่านั้น" และ rate limit ของ MailFast หรือไม่ อย่างไร | ไม่พูดถึง rate limit เลย; idempotency มีแค่ประโยคเดียวใน Risks | ใช้ `order_id` เป็น idempotency key, retry/backoff, dead-letter queue, จำกัดการส่ง ≤ 50/s และยอมรับว่าช่วงพีก backlog จะโต |
| มีสิ่งที่แต่งขึ้นเองหรือไม่ (ตัวเลข เครื่องมือ หรือข้อเท็จจริงที่ไม่มีใน scenario) | ไม่มี ย้ายสิ่งที่ไม่รู้ไปไว้ใน Open questions 8 ข้อแทน | ไม่พบข้อเท็จจริงที่แต่งขึ้น; Kafka, outbox และ publisher confirmation เป็นข้อเสนอด้านการออกแบบที่ AI เพิ่มเอง ไม่ได้มาจาก scenario |


## รับผิดชอบ ADR ฉบับสุดท้ายของตัวเอง

นิสิตคือสถาปนิก ให้คัดลอก `outputs/2b-adr.md` ไปที่ `docs/adr/0002-<short-title>.md` แล้วแก้ไข**ด้วยตัวเอง**จนพร้อมจะลงชื่อรับรอง ห้ามให้ agent ทำส่วนนี้

- แก้ไขสิ่งที่ผิดหรือแต่งขึ้นเอง และเพิ่มสิ่งที่ขาดหายไป
- ตัดสินใจขั้นสุดท้ายด้วยตัวเอง นิสิตสามารถไม่เห็นด้วยกับ AI ได้

## ตอบ
| # | สิ่งที่เปลี่ยนจากร่างของ AI | เหตุผล |
|---|---|---|
| 1 | เปลี่ยน Deciders จาก "ทีมพัฒนา Online Boutique (รอยืนยัน)" เป็น "ทีมพัฒนาสถาปัตยกรรมซอฟต์แวร์ Online Boutique" | ให้มีผู้รับผิดชอบชัดเจน พร้อมลงชื่อรับรอง |
| 2 | เพิ่มกลไก Fallback เมื่อ RabbitMQ หรือ Outbox ขัดข้องชั่วคราว | ไม่ให้การส่งข้อความล่มแล้วกระทบการบันทึกคำสั่งซื้อ |
| 3 | เพิ่มแนวทางระบาย Backlog ของอีเมลช่วงพีก (token bucket, alert, SLA) แทนย่อหน้าเดิมที่บอกแค่ว่าคิวดูดซับความผันผวนเท่านั้น | 200 orders/s เกิน rate limit 50 อีเมล/วินาทีของ MailFast ถึง 4 เท่า คิวจึงโตต่อเนื่อง ต้องตกลง SLA กับธุรกิจ |
| 4 | เปลี่ยน Open question สุดท้ายเป็น "คณะกรรมการและธุรกิจอนุมัติ SLA ของอีเมลช่วงพีกแล้วหรือยัง" | ตัดสินใจเลือก RabbitMQ เองแล้ว คำถามที่ยังค้างจึงเป็นเรื่อง SLA |
