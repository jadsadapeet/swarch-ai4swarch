# ADR-0002: แยกงานหลังสั่งซื้อด้วย RabbitMQ

- **Status:** Proposed
- **Date:** 2026-10-21
- **Deciders:** ทีมพัฒนา Online Boutique (รอยืนยัน)

## Context and problem

ปัจจุบัน `checkoutservice.PlaceOrder` เรียก `paymentservice`, `shippingservice` และ `emailservice` แบบ synchronous ผ่าน gRPC ตามลำดับ หากการส่งอีเมลล้มเหลว checkout จะบันทึกคำเตือนและยังส่งคำสั่งซื้อกลับว่าสำเร็จ โดยโค้ดไม่ได้แสดงการบันทึกคำสั่งซื้อแบบถาวร

ข้อกำหนด R-12 เพิ่มงานหลังสั่งซื้อสามอย่าง ได้แก่ ส่งอีเมลยืนยันผ่าน MailFast แทน logic จำลองเดิม ให้แต้มผ่าน `loyaltyservice` ใหม่ และบันทึก analytics event "order placed" ให้ทีมการตลาด อีกทั้งคาดว่าจะมีงาน SMS การให้คะแนนความเสี่ยงการทุจริต และการอัปเดตระบบแนะนำสินค้าในปีหน้า

`PlaceOrder` ต้องมี p95 ไม่เกิน 500 ms (ปัจจุบันประมาณ 300 ms) ที่ปริมาณสูงสุด 200 คำสั่งซื้อต่อวินาที MailFast มี p95 1.5 วินาที p99 8 วินาที อัตราล้มเหลวประมาณ 0.5% และจำกัดที่ 50 อีเมลต่อวินาที ดังนั้นการรอผู้ให้บริการอีเมลหรือบริการหลังสั่งซื้ออื่นใน request path ไม่เหมาะสม นอกจากนี้คำสั่งซื้อต้องไม่ล้มเหลวเมื่อบริการเหล่านี้หยุดทำงาน และแต้มต้องได้รับภายในหนึ่งนาทีโดยไม่ให้ซ้ำ

ระบบทำงานบน Kubernetes บริษัทต้องการ component แบบ open-source ที่ติดตั้งเอง ทีมมีนักพัฒนา 4 คนที่ถนัด Go และ gRPC โดย 2 คนมีประสบการณ์ RabbitMQ

## Decision drivers

- **ความพร้อมใช้งาน:** ความล้มเหลวหรือการหยุดทำงานของ MailFast, loyalty หรือ analytics ต้องไม่ทำให้คำสั่งซื้อล้มเหลว
- **ประสิทธิภาพ:** รักษา p95 ของ `PlaceOrder` ไม่เกิน 500 ms แม้มี 200 คำสั่งซื้อต่อวินาที และไม่รอ MailFast ที่ p95 1.5 วินาที
- **ความถูกต้องและความทนทาน:** ให้แต้มภายใน 1 นาทีและไม่ให้ซ้ำ แม้มีการ retry หรือ consumer ทำงานซ้ำ
- **การขยายตัว:** เพิ่ม consumer สำหรับงานหลังสั่งซื้อใหม่ได้โดยไม่เพิ่มการเรียก synchronous ใน checkout
- **การปฏิบัติการและทักษะทีม:** ใช้ระบบ open-source ที่ติดตั้งบน Kubernetes ได้ และสอดคล้องกับประสบการณ์ RabbitMQ ที่มีอยู่

## Considered options

1. เรียกบริการหลังสั่งซื้อทั้งหมดแบบ synchronous ผ่าน gRPC จาก `checkoutservice`
2. ใช้ RabbitMQ เป็น message broker สำหรับงานหลังสั่งซื้อแบบ asynchronous
3. ใช้ Kafka เป็น event streaming platform สำหรับเหตุการณ์หลังสั่งซื้อ

### Pros and cons of the options

| Option | Pros | Cons |
|---|---|---|
| Synchronous gRPC | เส้นทางการทำงานตรงไปตรงมา; ผลลัพธ์ของแต่ละการเรียกทราบได้ทันที | เพิ่ม latency และผูกความพร้อมใช้งานของ checkout กับบริการปลายทาง; MailFast ช้ากว่าเป้าหมาย checkout และจำกัดอัตราต่ำกว่าปริมาณคำสั่งซื้อช่วงพีก |
| RabbitMQ | Open-source และติดตั้งบน Kubernetes ได้; ทีมบางส่วนมีประสบการณ์; คิวช่วยแยก checkout ออกจาก consumer และรองรับการกระจายงานไปยังแต่ละบริการ | เพิ่มภาระดูแล broker, คิว, retry และ dead-letter; ต้องจัดการข้อความซ้ำและความทนทานของการส่งเหตุการณ์ |
| Kafka | Open-source; รองรับ event stream และผู้บริโภคหลายกลุ่ม | เพิ่มภาระปฏิบัติการ; ไม่พบข้อกำหนดเรื่อง replay หรือปริมาณ/การเก็บ event ที่ทำให้ความสามารถด้าน stream คุ้มกับความซับซ้อนเมื่อเทียบกับ RabbitMQ |

## Decision

เลือก **RabbitMQ** สำหรับการส่งเหตุการณ์หลังสั่งซื้อแบบ asynchronous โดยให้ `checkoutservice` สร้างเหตุการณ์ `OrderPlaced` ที่มี `order_id` คงที่ แล้วส่งผ่าน exchange ไปยังคิวแยกสำหรับอีเมล แต้มสะสม และ analytics แต่ละ consumer ประมวลผลและ retry ของตนเอง; การล้มเหลวหรือคิวค้างของ consumer หนึ่งจึงไม่ขัดขวาง consumer อื่นหรือทำให้ checkout รอผล

ใช้ durable message/queue และ publisher confirmation พร้อม transactional outbox ที่ผูกกับการบันทึกคำสั่งซื้อ เพื่อให้ relay ส่งเหตุการณ์ซ้ำได้เมื่อ broker ใช้งานไม่ได้ชั่วคราวโดยไม่ทำเหตุการณ์สูญหาย ทั้งนี้ต้องกำหนดแหล่งเก็บคำสั่งซื้อและ outbox ซึ่งปัจจุบันยังไม่ปรากฏใน `checkoutservice` ก่อนนำแนวทางนี้ไปใช้จริง

consumer ของ loyalty ต้องใช้ `order_id` เป็น idempotency key และบันทึกการประมวลผลอย่างทนทาน เพื่อให้การส่งซ้ำไม่เพิ่มแต้มซ้ำ ตั้ง retry/backoff และ dead-letter queue สำหรับข้อความที่ประมวลผลไม่สำเร็จอย่างต่อเนื่อง ส่วน consumer อีเมลต้องจำกัดการส่งไม่เกิน 50 อีเมลต่อวินาทีตาม MailFast

การเข้าคิวแยก checkout จากบริการปลายทางและรองรับการเพิ่มงานใหม่โดยเพิ่ม consumer ได้ โดยไม่เปลี่ยนเส้นทาง request หลัก อย่างไรก็ตามคิวช่วยดูดซับความผันผวนเท่านั้น: MailFast จำกัดไว้ที่ 50 อีเมลต่อวินาที เทียบกับพีก 200 คำสั่งซื้อต่อวินาที จึงไม่อาจรับประกันการส่งอีเมลทันทีหรือการระบายคิวระหว่างช่วงพีกได้หากไม่มีข้อมูลระยะเวลาพีกและนโยบายจัดการ backlog เพิ่มเติม

## Consequences

- **Positive:** ความล้มเหลวหรือความช้าของ consumer ไม่เพิ่มเวลารอใน `PlaceOrder` และไม่ทำให้คำสั่งซื้อล้มเหลว (ความพร้อมใช้งาน, ประสิทธิภาพ)
- **Positive:** คิวแยกตามงานช่วยให้เพิ่ม SMS, fraud scoring หรือการอัปเดตระบบแนะนำสินค้าได้ โดยไม่เพิ่มการเรียก synchronous ใน checkout (การขยายตัว, modifiability)
- **Positive:** `order_id` แบบคงที่และการประมวลผล loyalty แบบ idempotent ป้องกันการให้แต้มซ้ำจากการส่งข้อความซ้ำ (ความถูกต้อง)
- **Negative:** RabbitMQ และ outbox เพิ่ม component และงานด้านการติดตั้ง เฝ้าระวัง สำรอง/กู้คืน และดูแลคิว (ความสามารถในการปฏิบัติการ)
- **Negative:** การประมวลผลแบบ asynchronous ทำให้การส่งอีเมล แต้ม และ analytics ไม่เสร็จพร้อมกับการตอบกลับ checkout; ระบบต้องติดตามสถานะและ backlog แทนการพึ่งผลลัพธ์ทันที
- **Risks and mitigations:** broker หยุดทำงานหรือข้อความประมวลผลซ้ำอาจทำให้เกิดความล่าช้าหรือผลซ้ำ ใช้ outbox, durable queues, publisher confirmation, retry แบบจำกัดพร้อม dead-letter queue และ idempotency ฝั่ง consumer; แจ้งเตือนเมื่อ backlog เสี่ยงทำให้แต้มเกินหนึ่งนาที
- **Risks and mitigations:** ปริมาณอีเมลช่วงพีกสูงกว่า rate limit ของ MailFast ถึง 4 เท่า จำกัดอัตราส่งและเฝ้าระวังอายุ/ขนาดคิว แต่ต้องตกลงกับธุรกิจเรื่องระยะเวลาส่งที่ยอมรับได้และการรับมือช่วงพีกก่อนรับรอง SLA ของอีเมล

## Validation

- ทดสอบโหลด `PlaceOrder` ที่ 200 คำสั่งซื้อต่อวินาที และยืนยันว่า p95 ไม่เกิน 500 ms เมื่อ MailFast ช้า (รวมถึง p99 8 วินาที) ล้มเหลว หรือ consumer อื่นหยุดทำงาน
- ปิด MailFast, loyalty และ analytics แยกกัน แล้วตรวจว่าคำสั่งซื้อยังสำเร็จ ข้อความถูกเก็บ/ส่งต่อหลังระบบกลับมา และคิวของแต่ละงานไม่ขัดขวางกัน
- ทดสอบส่ง/ประมวลผลเหตุการณ์ loyalty ซ้ำและ retry พร้อมกัน แล้วตรวจว่ามีการเพิ่มแต้มเพียงครั้งเดียวต่อ `order_id` และแต้มถูกให้ภายใน 60 วินาทีภายใต้โหลดเป้าหมาย
- ตรวจสอบ durable queue, publisher confirmation, outbox relay, retry/backoff และ dead-letter queue โดยจำลอง broker restart และข้อความที่ consumer ปฏิเสธซ้ำ
- ทดสอบ rate limiter ของ MailFast ไม่ให้เกิน 50 อีเมลต่อวินาที และวัด backlog/อายุข้อความระหว่างโหลด 200 คำสั่งซื้อต่อวินาที เพื่อใช้ตกลง SLA การส่งอีเมลและแผนระบาย backlog

## Open questions

- จะใช้ที่เก็บข้อมูลใดเป็นแหล่งข้อมูลหลักของคำสั่งซื้อและ transactional outbox และจะทำให้การบันทึกคำสั่งซื้อกับ outbox สอดคล้องกับขั้นตอนชำระเงิน/จัดส่งอย่างไร?
- MailFast ยอมรับการส่งแบบใด มีนโยบาย retry/idempotency หรือไม่ และธุรกิจยอมรับเวลาส่งอีเมลสูงสุดหรือ backlog เท่าใดในช่วงที่มี 200 คำสั่งซื้อต่อวินาที แต่ส่งได้ไม่เกิน 50 อีเมลต่อวินาที?
- ต้องเก็บเหตุการณ์และข้อความในคิวนานเท่าใด และใครเป็นผู้รับผิดชอบการ replay หรือแก้ไขข้อความใน dead-letter queue?
- มีข้อกำหนดด้านความทนทาน/ความพร้อมใช้งานและการกู้คืนของ RabbitMQ ใน production อย่างไร?
- ใครเป็นผู้อนุมัติการตัดสินใจนี้ และทีมยืนยันให้ RabbitMQ เป็น broker ที่เลือกหรือไม่?
